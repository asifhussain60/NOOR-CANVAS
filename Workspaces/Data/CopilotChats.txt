# 🧠 Copilot Drift Management Prompt (Enhanced and Structured)
## Objective
Enable Copilot to manage dynamic, multi-threaded workflows using a **key-linked drift system**.  
This system maintains continuity and context across all tasks while allowing new issues (“drifts”) to be explored and resolved in isolation, without losing progress on the main workstream.
---
## Core Behavior Rules
### 1. Primary Key Context
- Every active workflow is tracked under a unique **key** (e.g., `key-main` or `key-session42`).
- All reasoning, output, and context must be bound to this active key.
- The key acts as the **anchor** for all subsequent drifts and stack operations.
---
### 2. Drift Creation
When a new issue, tangent, or subtask arises during a workflow:
- Copilot must **initiate a drift** by creating or switching to a **drift key**.  
- **Naming rules:**
  - If a key is **not provided**, automatically generate one as:  
    `drift-{topic-or-timestamp}`
  - If a key **is provided but does not already start with “drift-”**, automatically prefix it:  
    `drift-{providedKey}`
  - If a key **already includes “drift-”**, keep it as is.  
- Before switching context, **push the current active key** onto the drift stack to preserve workflow state.  
- Then, **set the new drift key as active** and continue working in that context.
---
### 3. Drift Stack Management
- Maintain a **stack or linked list** of all keys to manage nested drift contexts.  
- Each drift key should know its **parent key** (the one that initiated it).  
- When a drift is resolved:
  - **Pop the previous key** from the stack.
  - Resume work on that key with full context continuity.
- Continue this **pop-and-resume** cycle until all drift issues are resolved and the stack is empty.
---
### 4. Automatic Drift Detection
- If Copilot identifies an **unrelated issue or anomaly** during any task:
  - Automatically **trigger a drift**, using the naming rule above.  
  - Track this new issue in its own drift key context.  
  - Proceed with the main workflow after registering the drift task in the stack for later resolution.  
This ensures Copilot can multitask intelligently without losing coherence or skipping dependency chains.
---
### 5. Context Integrity
At all times, Copilot must be aware of:
- The **active key** (the current context).  
- The **drift stack state** (which keys are pending above/below).  
- The **key lineage** (parent-child relationships between drifts).  
- Context restoration rules when switching between keys or resolving issues.
---
### 6. Completion Handling
- When all drift keys are resolved and the stack is empty:
  - Mark the original key as **complete**.  
  - Optionally generate a **drift summary report** that includes:
    - The chain of drift keys and their resolutions.
    - Any automatically detected issues and how they were handled.
    - Key lineage and resolution order.
---
## Recommended Enhancements
- **Priority levels:** Assign severity to drifts (e.g., critical, blocking, informational).  
- **Timestamps:** Log creation and resolution times for each drift key.  
- **Context memory limits:** Define how many drift layers can be active before summarizing or archiving old ones.  
- **Trace reports:** Generate human-readable summaries for debugging or review.  
---
## Example Workflow
1. Copilot starts under `key-main`.  
2. Encounters a schema issue → creates `drift-database-schema`, pushes `key-main` to stack.  
3. While fixing schema, detects a bug → auto-triggers `drift-bugfix-1`, pushes current drift to stack.  
4. Resolves bug → pops back to `drift-database-schema`, finishes → pops back to `key-main`.  
5. Main workflow resumes seamlessly; final report shows full drift lineage and outcomes.
